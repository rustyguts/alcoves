# Backend Top 10 Improvement Plan

> Generated by a multi-agent audit: 12 Sonnet workers scanned every package under
> `backend/internal/` (~15.8k LOC) across **performance, design, efficiency, and
> security**, producing 106 raw findings. A synthesis pass deduplicated and ranked
> the top 10 by category priority (performance → design → efficiency → security),
> then by impact within each category.

**Audit date:** 2026-06-02  ·  **Raw findings:** 106  ·  **Selected:** 10

## Executive summary

The Alcoves backend has critical issues across all four categories. Two SQL injection vulnerabilities exist in the hot file-listing service path where raw fmt.Sprintf constructs queries from unvalidated URL parameters. Memory exhaustion risks are present in both video proxy (full file buffered for every range request) and audio workers (full PCM loaded per job). The admin job queue routes are completely unprotected by the owner-only middleware, allowing any authenticated member to purge the entire work queue. The CORS policy reflects every origin with AllowCredentials:true, and the file proxy endpoint is fully unauthenticated — together these represent complete session-hijack and data-exfiltration vectors for any self-hosted instance.

## Performance

### 1. SQL injection via unvalidated libraryID/folderID interpolated into raw listing queries

- **Category:** Performance  ·  **Impact:** 5/5  ·  **Effort:** M
- **Affected files:**
  - `internal/services/files/listing.go`

**Problem**

buildFolderQueries and buildFileQueries construct raw SQL via fmt.Sprintf, interpolating libraryID (from the URL path param, never uuid.Parse'd in the handler) and currentFolderID (from normalizeFolderID, which only trims whitespace) directly into single-quoted strings. The escapeSQLString helper only doubles single quotes, which is not injection-proof under non-standard PostgreSQL client encodings. Additionally, cursor.SortName (decoded from a user-supplied base64 string) is interpolated the same way. Any authenticated library member can exfiltrate arbitrary table data via a crafted ?folder= or ?cursor= parameter on the GET /api/libraries/:id/files endpoint — the hottest read path in the application.

**Evidence**

listing.go:351 `where = fmt.Sprintf("library_id = '%s' AND ... parent_folder_id = '%s'", libraryID, *currentFolderID)`. listing.go:363-364 cursor SortName interpolated via escapeSQLString. listing.go:717-723 normalizeFolderID does no uuid.Parse. Handler line 71 passes raw c.Param("id") without validation.

**Implementation plan**

1. In the handler (internal/handlers/file.go, ListLibraryFiles entry point): call uuid.Parse(c.Param("id")) for libraryID and return 400 on failure, matching the existing pattern at file.go:80.
2. In listing.go normalizeFolderID (line 717): after the empty/null check, call uuid.Parse(s); if it fails return nil (treat as root) or propagate a validation error up through ListLibraryFiles.
3. Refactor buildFolderQueries and buildFileQueries to return (string, []interface{}) — a parameterised query string with ? placeholders and a matching args slice. Replace every fmt.Sprintf with a strings.Builder + append-to-args pattern.
4. In parseCursor (listing.go ~700), add a max-length check on SortName (e.g. 500 chars) and remove the escapeSQLString call from the cursor-where construction; use a ? placeholder for SortName in the returned args slice.
5. Update all callers of buildFolderQueries/buildFileQueries to pass the args slice to s.db.Raw(query, args...).Scan(...).
6. Run go test ./internal/services/files/... -race -count=1 and verify existing listing tests still pass; add a test with folder=../../ to confirm it is rejected as invalid UUID.

**Risks:** Refactoring the query builders touches the hottest read path. Ensure the GORM Raw positional-param syntax matches PostgreSQL's $1/$2 convention (GORM translates ? to $N for pgx). Run a full regression on pagination cursors before merging.

**Verification:** Unit test: inject folder=x'OR'1'='1 and assert 400 returned. Integration test: valid UUID folder returns correct results. EXPLAIN on the parameterised query to confirm index use is unchanged.

### 2. No pgvector index on face_detections.embedding — every clustering query is a full sequential scan

- **Category:** Performance  ·  **Impact:** 5/5  ·  **Effort:** S
- **Affected files:**
  - `internal/services/facedetection/clustering.go`
  - `migrations/00001_initial_schema.sql`

**Problem**

AssignFaceUsingCorePoint and ReconcileNewPerson both issue ORDER BY fd.embedding <=> $1::vector LIMIT N queries (cosine ANN) against face_detections. The schema creates only B-tree indexes on file_id, library_id, and person_id — no IVFFlat or HNSW index on embedding. Every cosine-distance lookup performs a full sequential scan of all rows for the library, holding a DB connection for the full duration. ReconcileNewPerson runs up to 5 such queries per new-person event. With 10k+ face rows per library (common for large photo collections) face clustering slows to a crawl and blocks asynq worker slots.

**Evidence**

migrations/00001_initial_schema.sql lines 183-185: only face_detections_file_id_idx, face_detections_library_id_idx, face_detections_person_id_idx. clustering.go lines 30-38: ORDER BY fd.embedding <=> $1::vector LIMIT $4 — no index hint.

**Implementation plan**

1. Create a new Goose migration file migrations/00006_face_embedding_hnsw_idx.sql (next available number after checking existing migrations).
2. In the +goose Up block add: CREATE INDEX CONCURRENTLY IF NOT EXISTS face_detections_embedding_hnsw_idx ON face_detections USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
3. In the +goose Down block add: DROP INDEX IF EXISTS face_detections_embedding_hnsw_idx;
4. At query time in clustering.go, prepend SET LOCAL hnsw.ef_search = 40; inside the transaction before issuing the ANN query, or set it at connection-pool level via pgx AfterConnect hook.
5. Add AND fd.library_id = $2 to the WHERE clause in AssignFaceUsingCorePoint (clustering.go:32) to allow the planner to filter-then-scan the index rather than scanning all libraries.
6. Run EXPLAIN (ANALYZE, BUFFERS) on the ANN query after migration to confirm index scan is used.
7. Run go test ./internal/services/facedetection/... to verify no test regressions.

**Risks:** CONCURRENTLY requires the migration to run outside a transaction block — Goose supports this via -- +goose NO TRANSACTION annotation. On an existing production database with many rows, index build may take minutes; schedule during low-traffic window. HNSW recall is approximate; verify clustering quality is unchanged after rollout.

**Verification:** EXPLAIN on SELECT ... ORDER BY embedding <=> ? LIMIT 10 should show 'Index Scan using face_detections_embedding_hnsw_idx'. Benchmark face:detect task duration before and after on a library with 5k+ detections.

### 3. Legacy proxy video handler reads entire file into RAM on every range request

- **Category:** Performance  ·  **Impact:** 4/5  ·  **Effort:** M
- **Affected files:**
  - `internal/handlers/file.go`
  - `internal/services/storage/storage.go`

**Problem**

The legacy Proxy code path (file.go:929) calls ReadCacheBuffer which calls os.ReadFile, loading the full proxy.mp4 into a []byte before slicing it for HTTP range requests. A 2 GB proxy file means 2 GB of heap allocation per concurrent video playback session. With eight concurrent asynq workers and multiple simultaneous browser video sessions, the process will OOM. The storage layer already has OpenCacheReadStreamRange which supports range-aware streaming but is unused here. The same pattern exists for thumbnails (line 989) and waveform JSON (line 740), though those are smaller.

**Evidence**

file.go:929 `data, err := h.storageSvc.ReadCacheBuffer(cacheKey)` — ReadCacheBuffer calls os.ReadFile. file.go:938 `totalSize := int64(len(data))` confirms full slice held in memory. storage.go:115 OpenCacheReadStreamRange exists and supports byte-range streaming.

**Implementation plan**

1. In the Proxy handler (file.go ~923), replace ReadCacheBuffer with a two-step approach: call h.storageSvc.CacheStat(cacheKey) to get totalSize, then call h.storageSvc.OpenCacheReadStreamRange(cacheKey, byteRange) for the actual data.
2. Parse the Range header first (reuse the existing rangeRegex at file.go:940); compute start/end/clamp against totalSize; then open only the needed byte range.
3. Write the Content-Range and Content-Length headers, open the stream, defer rc.Close(), and use c.Stream(206, "video/mp4", rc) for range responses or c.Stream(200, "video/mp4", rc) for full responses.
4. Apply the same ReadCacheBuffer→OpenCacheReadStream swap for the thumbnail endpoint (file.go:989) and waveform endpoint (file.go:740) where streaming is simpler (no range needed): use h.storageSvc.OpenCacheReadStream and c.Stream(200, mimeType, rc).
5. Remove the now-unused ReadCacheBuffer call sites; if ReadCacheBuffer has no remaining callers, mark it deprecated or remove it.
6. Run go test ./internal/handlers/... -race -count=1; add a test that asserts the proxy handler returns 206 for a Range request without loading the full file (mock storage).

**Risks:** The new streaming path must correctly set Content-Length so browsers can display seek bars. Test with Safari (which is stricter about byte-range compliance). Ensure OpenCacheReadStreamRange returns io.EOF at the correct boundary — test with a range that ends exactly at the file boundary.

**Verification:** Memory profile (pprof heap) during concurrent video playback should show no large []byte allocations correlated with file size. HTTP response headers should include Content-Range: bytes start-end/total and correct Content-Length.

### 4. Full PCM file read into RAM per audio-detection and waveform worker job

- **Category:** Performance  ·  **Impact:** 4/5  ·  **Effort:** M
- **Affected files:**
  - `internal/services/waveform/worker.go`
  - `internal/services/audiodetection/worker.go`

**Problem**

computePeaks in waveform/worker.go:210 calls os.ReadFile to load the entire extracted PCM into a single []byte. audiodetection/worker.go readFloat32PCM (line ~270) does the same at 32 kHz. For a 2-hour file at 16 kHz float32 mono the PCM is ~460 MB; at 32 kHz it is ~920 MB. With asynq Concurrency=8, peak RSS from audio workers alone can reach several GB, triggering OOM kills. Neither function uses streaming or chunking.

**Evidence**

waveform/worker.go:210 `data, err := os.ReadFile(pcmPath)` — entire PCM loaded before any peak computed. The computePeaks loop then walks data in windowSize chunks, meaning the full allocation is held for the entire computation.

**Implementation plan**

1. In waveform/worker.go computePeaks: replace os.ReadFile with os.Open to get an *os.File, wrap with bufio.NewReaderSize(f, 64*1024), and read exactly windowSize*4 bytes per iteration using io.ReadFull.
2. Compute the peak for each window immediately and append to peaks, then advance to the next window — no full-file buffer is ever allocated.
3. In audiodetection/worker.go readFloat32PCM: use the same os.Open + bufio.Reader approach; decode float32 samples in chunks matching the inference window size (cfg.AudioDetectWindowSec * sampleRateHz * 4 bytes), feeding each chunk directly into the inference loop.
4. Remove the intermediate []float32 full-file slice in readFloat32PCM; instead pass a pre-allocated window-size buffer that is reused across iterations.
5. Update the function signatures if needed: computePeaks(pcmPath string, peaksPerSec int) and the audiodetection equivalent should both accept a path (already the case) and return error.
6. Run go test ./internal/services/waveform/... ./internal/services/audiodetection/... -race -count=1. Add a test with a known synthetic PCM file and assert peak values are unchanged.

**Risks:** Streaming changes the memory access pattern; verify that partial final windows (when file length is not a multiple of windowSize) are handled identically to the current implementation (padding with zeros or truncating). The audiodetection chunked path must produce identical inference results to the batch path.

**Verification:** Run runtime/pprof heap profile during a waveform task on a long audio file; confirm peak alloc is O(window_size) not O(file_size). Compare peak arrays from streaming vs. bulk implementations on a reference file to confirm numerical identity.

### 5. N+1 breadcrumb query: one DB round-trip per folder depth level on every file-listing page load

- **Category:** Performance  ·  **Impact:** 3/5  ·  **Effort:** S
- **Affected files:**
  - `internal/services/files/listing.go`

**Problem**

getFolderBreadcrumbs walks the folder ancestry one row at a time in a Go loop, issuing one SELECT per ancestor. A folder nested 10 levels deep generates 10 serial DB round-trips on every non-root page load. This is on the critical hot path — every file browser render hits getFolderBreadcrumbs. The pattern can be fully replaced with a single recursive CTE that PostgreSQL resolves in one round-trip regardless of depth.

**Evidence**

listing.go:436-461: `for currentID != "" { err := s.db.Raw("SELECT id, name, parent_folder_id FROM folders WHERE id = ? AND library_id = ? ...", currentID, libraryID).Scan(&folder).Error ... }` — sequential loop, one query per ancestor.

**Implementation plan**

1. Replace the entire getFolderBreadcrumbs loop body with a single recursive CTE query using s.db.Raw(...).Scan(&rows).
2. Use: WITH RECURSIVE breadcrumb AS (SELECT id, name, parent_folder_id, 0 AS depth FROM folders WHERE id = ? AND library_id = ? AND trashed_at IS NULL UNION ALL SELECT f.id, f.name, f.parent_folder_id, b.depth+1 FROM folders f JOIN breadcrumb b ON f.id = b.parent_folder_id WHERE f.library_id = ? AND f.trashed_at IS NULL) SELECT id, name, depth FROM breadcrumb ORDER BY depth DESC. Pass folderID, libraryID, libraryID as args.
3. Add a LIMIT 50 to the CTE to guard against corrupt circular hierarchies (replace the visited map cycle-detection).
4. Map the query results (already sorted deepest-first by ORDER BY depth DESC) directly to []FolderBreadcrumb without the separate reverse loop.
5. Add s.db.WithContext(ctx) to this call (part of the broader context-propagation effort) once the context parameter is threaded through ListLibraryFiles.
6. Write a unit test for getFolderBreadcrumbs that exercises a 5-level deep folder hierarchy and asserts the returned breadcrumb order is root-to-leaf.

**Risks:** The CTE relies on PostgreSQL's WITH RECURSIVE support (available since PG 8.4, no concern). The visited map guarded against infinite loops in corrupt data — the LIMIT 50 replacement must be documented. Verify the depth ORDER DESC correctly produces root→leaf order (depth 0 is the target folder, deepest number is root — ORDER DESC puts root first).

**Verification:** go test ./internal/services/files/... with a mock DB that counts query invocations — assert exactly one query is issued for a nested folder. Measure p95 latency of GET /api/libraries/:id/files?folder=<nested_id> in a load test before and after.

### 6. Admin job queue routes registered without owner-only middleware — any member can purge the work queue

- **Category:** Design  ·  **Impact:** 5/5  ·  **Effort:** S
- **Affected files:**
  - `internal/handlers/admin_jobs.go`
  - `cmd/server/main.go`

**Problem**

AdminHandler.RegisterRoutes applies g.Use(h.requireOwnerMiddleware) to its Echo group, but AdminJobsHandler.RegisterRoutes is registered on a separate api.Group("/admin") call in main.go with no middleware. Every authenticated user (role=member) can call POST /api/admin/jobs/:queueName/purge (deletes all queued work), POST /api/admin/jobs/:queueName/:jobId (retry/delete individual tasks), and GET /api/admin/jobs/stream (SSE stream of internal queue state). The purge endpoint is a destructive write operation with zero authorization.

**Evidence**

cmd/server/main.go:282 adminHandler.RegisterRoutes(api.Group("/admin")) — has middleware. main.go:293 adminJobsHandler.RegisterRoutes(api.Group("/admin")) — separate group, no middleware. admin_jobs.go:21-27 RegisterRoutes has no g.Use() call.

**Implementation plan**

1. In AdminJobsHandler (admin_jobs.go), add a requireOwnerMiddleware field: embed or reference the same owner check used by AdminHandler.
2. Option A (simplest): Pass the AdminHandler's requireOwnerMiddleware func as a parameter to NewAdminJobsHandler and call g.Use(h.ownerMW) inside RegisterRoutes.
3. Option B (cleaner): In main.go, merge both handlers' routes under a single shared admin group: adminGroup := api.Group("/admin"); adminGroup.Use(adminHandler.RequireOwnerMiddleware()); adminHandler.RegisterRoutesOn(adminGroup); adminJobsHandler.RegisterRoutesOn(adminGroup). Export RequireOwnerMiddleware() from AdminHandler.
4. Remove the separate api.Group("/admin") call on line 293 of main.go so there is exactly one admin group.
5. Add an integration test in admin_test.go asserting that a member-role session receives 403 from GET /api/admin/jobs/stats and POST /api/admin/jobs/default/purge.
6. Run go test ./internal/handlers/... -run TestAdmin -v.

**Risks:** If any admin UI polling routes are called frequently, the extra middleware adds a DB lookup per call — this is acceptable given the sensitivity of the endpoint. Verify the echo group merge does not change the route paths (both use /admin prefix, combining them is transparent).

**Verification:** curl -s -X POST /api/admin/jobs/default/purge with a member-session cookie must return 403. curl with owner-session cookie must succeed. go test ./internal/handlers/... -race -count=1.

### 7. Non-atomic user registration: account and library creation errors silently swallowed, leaving orphaned users

- **Category:** Design  ·  **Impact:** 3/5  ·  **Effort:** S
- **Affected files:**
  - `internal/handlers/auth.go`
  - `internal/handlers/oauth.go`

**Problem**

Register creates the User row, then creates the Account row, then creates the Library row as three independent DB operations with no wrapping transaction. GoogleCallback has the same pattern. If Account or Library creation fails (DB constraint, connectivity blip), the User row is left orphaned: no credential account and no default library, making the app broken for that user with no recovery path. Errors from Account and Library creation are silently discarded in both handlers.

**Evidence**

auth.go:149 `h.db.Create(&account)` return value ignored. auth.go:157 `h.db.Create(&library)` return value ignored. oauth.go:166 `h.db.Create(&user)` unchecked. oauth.go:169-173 `h.db.Create(&models.Library{...})` unchecked. oauth.go:177-181 `h.db.Create(&models.Account{...})` unchecked.

**Implementation plan**

1. In auth.go Register, wrap lines 139-164 (user + account + library creation) in h.db.Transaction(func(tx *gorm.DB) error { ... }), replacing h.db with tx for all three Create calls inside.
2. Check and propagate errors from tx.Create(&account) and tx.Create(&library) — return the error to roll back the transaction.
3. Move the invite redemption (lines 165+) to outside and after the transaction commit, since Redeem already uses its own transaction internally.
4. In oauth.go GoogleCallback, apply the same pattern: wrap user + library + account creation (lines 158-181) in h.db.Transaction(func(tx *gorm.DB) error { ... }).
5. Add explicit error checks for each tx.Create call inside both transaction functions; return the error to trigger rollback.
6. Update auth_test.go and oauth_test.go: add a test that simulates a DB error on account creation and asserts the user row is not left in the database.

**Risks:** The invite redemption (Redeem) must stay outside the registration transaction because it opens its own transaction. Nesting transactions in GORM uses savepoints; confirm the Go GORM version supports nested transactions (gorm.io/gorm v1.23+ does via SavePoint). Test with PostgreSQL's pgx driver that savepoints work correctly.

**Verification:** Unit test: mock the DB to fail on the Account insert; assert no User row remains. go test ./internal/handlers/... -run TestRegister -race -count=1.

## Efficiency

### 8. Audio-detection ONNX session reloaded from disk on every task — brute-force probe repeated 30 times per file

- **Category:** Efficiency  ·  **Impact:** 3/5  ·  **Effort:** S
- **Affected files:**
  - `internal/services/audiodetection/worker.go`
  - `internal/services/audiodetection/models.go`

**Problem**

LoadSession is called in audiodetection/worker.go:117 on every task invocation. It tries up to 30 input/output name combinations (6×5), each of which calls ort.NewDynamicAdvancedSession to load the ~100 MB ONNX model from disk and runs a probe inference, before finding the right pair and discarding all the rest. facedetection and objectdetection both use package-level sync.Once to load their sessions exactly once. The audiodetection service performs this expensive brute-force for every enqueued file, adding several seconds of overhead per task and loading/unloading a 100 MB model repeatedly.

**Evidence**

audiodetection/worker.go:117 `sess, err := LoadSession(modelPath)` — no caching. objectdetection/worker.go:36 `sessionOnce sync.Once` — loaded once. audiodetection/models.go:190-219: 6×5=30 probe combinations attempted on every call.

**Implementation plan**

1. Add package-level variables to audiodetection/worker.go (or a new audiodetection/session.go file): `var ( sessionOnce sync.Once; cachedSession *sessionInfo; sessionErr error )`.
2. Create a getSession(modelPath string) (*sessionInfo, error) function that wraps sessionOnce.Do(func() { cachedSession, sessionErr = LoadSession(modelPath) }) and returns cachedSession, sessionErr — mirroring objectdetection/worker.go:50-54.
3. In TaskHandler.ProcessTask, replace the direct LoadSession(modelPath) call with getSession(modelPath).
4. Remove the `defer sess.session.Destroy()` call that currently runs after each task — the cached session must not be destroyed between tasks; destroy only on process shutdown via a registered cleanup hook or os.Signal handler.
5. To handle the sync.Once-permanent-error problem (a transient model-load failure poisons the handler forever), use a sync.Mutex + flag instead of sync.Once: if sessionErr != nil { reset flag, retry on next call } — or document that EnsureAssets must succeed before workers start.
6. Run go test ./internal/services/audiodetection/... and measure task processing time with a synthetic short audio clip before and after.

**Risks:** The ONNX session is not goroutine-safe for concurrent inference; verify that asynq's per-task goroutines do not call Run() concurrently on the same session. If they do, protect sess.session.Run() with a sync.Mutex or load one session per worker goroutine. Check ort.DynamicAdvancedSession documentation for thread-safety guarantees.

**Verification:** Add a counter to LoadSession that increments each call; assert it is called exactly once across 5 sequential task invocations in a test. Measure wall-clock time for audiodetect task processing — should drop by the LoadSession overhead (~2-5s depending on disk speed).

## Security

### 9. CORS reflects every origin with AllowCredentials:true — full cross-origin session hijack vector

- **Category:** Security  ·  **Impact:** 5/5  ·  **Effort:** S
- **Affected files:**
  - `cmd/server/main.go`

**Problem**

AllowOriginFunc unconditionally returns true for every request Origin, and AllowCredentials is also true. Any website can make credentialed cross-origin fetch() calls with the session cookie, bypassing same-origin protection. All mutating endpoints (DELETE library, PATCH files, POST moments/exports, POST admin/purge) are reachable from a malicious page visited by any logged-in user. SameSite=Lax partially mitigates simple navigations but does not block cross-origin fetch() with credentials.

**Evidence**

main.go:193 `AllowOriginFunc: func(origin string) (bool, error) { return true, nil }` combined with main.go:208 `AllowCredentials: true`. The comment on line 191 acknowledges the wildcard restriction but the dynamic-reflect workaround is semantically equivalent to * with credentials from the browser's perspective.

**Implementation plan**

1. In cmd/server/main.go, import net/url and parse cfg.BaseURL at startup: `parsedBase, err := url.Parse(cfg.BaseURL)` — fail fast if BaseURL is empty or invalid.
2. Build an explicit origin allowlist: `allowedOrigin := parsedBase.Scheme + "://" + parsedBase.Host`. Optionally add a second entry for localhost dev if cfg.Env == "development".
3. Replace the AllowOriginFunc lambda with: `func(origin string) (bool, error) { return origin == allowedOrigin, nil }`.
4. Add an ALCOVES_EXTRA_CORS_ORIGINS env var (comma-separated) parsed in config.go for deployments where the Nuxt frontend is on a different subdomain, and include those in the allowlist check.
5. Update the integration test suite (if any CORS tests exist) and add a test that sends Origin: https://evil.example.com and asserts Access-Control-Allow-Origin is absent from the response.
6. Run go test ./... -race -count=1 to ensure no handler tests rely on the open CORS policy.

**Risks:** If ALCOVES_BASE_URL is not set or is set incorrectly in a deployment, legitimate requests from the Nuxt frontend will be blocked. Add a clear startup-time validation log: 'CORS allowedOrigin: <value>'. For single-origin reverse-proxy deployments (Nuxt and Go behind the same nginx), CORS can be removed entirely — document this as a migration note.

**Verification:** curl -H 'Origin: https://evil.example.com' -I http://localhost:3001/api/health must not return Access-Control-Allow-Origin. curl -H 'Origin: <configured BaseURL>' must return it. Run a Playwright cross-origin test if the e2e suite covers auth flows.

### 10. File proxy endpoint is fully unauthenticated — any file in any private library is publicly readable

- **Category:** Security  ·  **Impact:** 5/5  ·  **Effort:** M
- **Affected files:**
  - `internal/middleware/auth.go`
  - `internal/handlers/download.go`

**Problem**

auth.go:87-89 unconditionally skips authentication for every URL matching /api/files/proxy/**. The proxy handler accepts libraryID and fileID from the URL path and serves the raw file (or a libvips-transformed variant) with no session check and no library membership check. An unauthenticated attacker who can enumerate or guess any valid UUID pair can download any file from any private library. This is the same endpoint that also lacks dimension bounds (finding #8 in the original list), meaning it is simultaneously an unauthenticated data-exfiltration and an unauthenticated DoS vector.

**Evidence**

auth.go:87-89: `if strings.HasPrefix(path, "/api/files/proxy/") { return false }` — needsAuth returns false unconditionally. download.go:180-181: `h.db.Where("id = ? AND library_id = ?", fileID, libraryID).First(&file)` — no user/membership predicate.

**Implementation plan**

1. Remove the public proxy exemption from auth.go:87-89 (`if strings.HasPrefix(path, "/api/files/proxy/") { return false }`).
2. In download.go Proxy handler, extract the authenticated userID from context (middleware.GetUserID(c)) after the auth middleware now runs.
3. Add a library membership check before serving: call h.accessSvc.GetLibraryAccess(c, userID, libraryID) (the same helper used by LibraryAccessMiddleware) and return 403 if access is denied.
4. Also add parseTransformOptions clamping in the same handler: enforce a maxDimension = 4096 cap on opts.Width and opts.Height to neutralise the concurrent DoS vector.
5. Update the auth middleware test (middleware/auth_test.go) to confirm /api/files/proxy/... now requires authentication.
6. If the frontend or any existing client relies on unauthenticated proxy URLs (e.g. for <img src=> in SSR pages that lack cookie forwarding), audit those call sites and ensure they use the API with proper cookie forwarding via useRequestHeaders(['cookie']) as documented in the Nuxt SSR pattern.

**Risks:** The Nuxt SSR pages render <img> tags using proxy URLs. On the server side (SSR), these are fetched without a browser cookie unless the Nuxt util/api-fetch.ts SSR cookie-forwarding pattern is applied. Audit app/pages/s/[token].vue and any library browser components that embed proxy image URLs to confirm they either (a) use session-cookie-forwarded fetch on SSR, or (b) switch to the authenticated /api/files route. This is a breaking change for any public embed use case.

**Verification:** curl -s http://localhost:3001/api/files/proxy/<libraryID>/<fileID> with no cookie must return 401. curl with a valid member session cookie for the correct library must return 200. curl with a valid session cookie for a different library must return 403.
